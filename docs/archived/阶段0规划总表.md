# 阶段 0 规划总表

> 本文档是阶段 0 的总控表，目的是梳理"还需要确定什么"以及"怎么拆文档"，而非直接给出最终规则。

---

## 1. 当前已经确定的项目前提

| 维度 | 已确定的内容 |
|------|-------------|
| 游戏类型 | 多人在线网页卡牌游戏 |
| 核心玩法 | 阵营扮演 + 隐藏信息 + 社交推理 |
| 目标玩家 | 朋友之间组房游玩 |
| 人数范围 | 3-6 人 |
| 风格参考 | 《诡秘之主》氛围（神秘学、组织对立、路径/序列、灰雾集会），非逐字复刻 |
| 技术方向 | Next.js + TypeScript + Socket.IO + Prisma + PostgreSQL |
| 部署目标 | 个人域名，朋友可访问 |
| 产品原则 | 先可玩再完善；先房间制再匹配制；先服务端权威再前端表现；先数据化规则再扩展内容 |
| 当前阶段目标 | 产出前期规划文档，不开发代码 |

## 2. 当前还未确定的核心问题清单

### 2.1 玩法设计层

| 编号 | 问题 | 为什么必须先确定 |
|------|------|----------------|
| Q1 | **单局核心循环是什么？**（出牌 → 揭示 → 讨论 → 投票 → 结算？还是其他节奏？） | 所有卡牌设计、角色技能、事件系统都依赖循环结构 |
| Q2 | **一局游戏的目标时长是多少？** | 影响回合数、卡牌数量、信息量上限 |
| Q3 | **胜利条件有哪些？**（阵营胜利？个人胜利？隐藏任务胜利？） | 直接决定阵营划分和角色设计方向 |
| Q4 | **阵营如何划分？**（固定阵营？随机分配？有内鬼？可转换？） | 影响角色分配逻辑和信息可见性规则 |
| Q5 | **信息隐藏的范围和方式？**（玩家能看到什么？手牌可见？身份可见？出牌历史可见？） | 影响 UI 信息层级和核心博弈设计 |
| Q6 | **卡牌体系的分类是什么？**（身份牌？行动牌？事件牌？道具牌？技能牌？） | 卡牌分类决定数据结构设计和后续扩展边界 |
| Q7 | **角色/序列体系如何设计？**（是否采用类似"途径"的晋升系统？还是固定角色池？） | 影响角色深度和策略空间 |

### 2.2 世界观与叙事层

| 编号 | 问题 | 为什么必须先确定 |
|------|------|----------------|
| Q8 | **原著引用边界在哪里？**（哪些元素可以直接用？哪些只能做氛围参考？哪些必须完全原创？） | 版权风险核心问题，影响所有文案和美术方向 |
| Q9 | **叙事是强剧情驱动还是弱剧情驱动？**（有固定剧本和事件线？还是纯玩法驱动？） | 决定是否需要剧本系统和剧情事件库 |
| Q10 | **游戏内的"世界观解释"如何呈现？**（开场介绍？卡牌描述？事件文本？独立设定页？） | 影响文档结构和前端呈现方式 |

### 2.3 技术与架构层

| 编号 | 问题 | 为什么必须先确定 |
|------|------|----------------|
| Q11 | **房间状态的权威模型是什么？**（一局游戏 = 一个状态机？状态包含哪些字段？） | 影响 Socket.IO 消息协议和数据库 schema |
| Q12 | **断线重连的策略？**（断线后保留多长时间？重连后如何恢复状态？观战模式？） | 影响房间管理和状态持久化设计 |
| Q13 | **是否需要房主控制系统？**（踢人、重开、暂停、规则自定义？） | 影响权限模型和前端控制逻辑 |

### 2.4 运营与合规层

| 编号 | 问题 | 为什么必须先确定 |
|------|------|----------------|
| Q14 | **美术素材的来源和版权？**（AI 生成？原创绘制？开源素材？原著相关素材？） | 直接影响上线风险 |
| Q15 | **是否需要用户系统？**（游客模式？注册登录？房间密码？） | 影响数据库设计和部署复杂度 |

## 3. 问题之间的依赖关系

```
Q8 (原著引用边界)
  ↓ 影响
Q9 (叙事驱动方式) → Q10 (世界观呈现方式)

Q1 (单局核心循环) ─┬→ Q2 (目标时长)
                    ├→ Q3 (胜利条件)
                    └→ Q5 (信息隐藏范围)

Q3 (胜利条件) ──→ Q4 (阵营划分) ──→ Q7 (角色体系)
Q4 (阵营划分) ──→ Q6 (卡牌分类)

Q11 (状态模型) ←── Q1 (单局核心循环)
Q11 (状态模型) ←── Q12 (断线重连策略)
Q11 (状态模型) ←── Q13 (房主控制系统)

Q15 (用户系统) ──→ Q12 (断线重连策略)
Q15 (用户系统) ──→ Q13 (房主控制系统)
```

**关键路径**：Q8 → Q1 → Q3 → Q4 → Q7 → Q6 → Q11

即：先确定原著边界 → 确定核心循环 → 确定胜利条件 → 确定阵营 → 确定角色 → 确定卡牌 → 确定技术状态模型。

## 5. 每份独立文档的目标、输入、输出

### D1 — 单局流程设计文档

| 维度 | 内容 |
|------|------|
| 目标 | 定义一局游戏从开始到结束的完整流程，包括每个阶段的玩家行为、信息可见性和状态转换 |
| 输入 | 已确定的项目前提（本文档第 1 节）、核心玩法关键词 |
| 输出 | 单局阶段划分表、每阶段的玩家行为描述、信息可见性矩阵、建议时长 |

### D2 — 剧情背景设定文档

| 维度 | 内容 |
|------|------|
| 目标 | 确定原著引用边界，定义游戏内世界观的原创程度，设定叙事驱动方式 |
| 输入 | Q8 的结论（原著边界）、Q9 的结论（叙事方式） |
| 输出 | 可用元素清单、禁用元素清单、原创替换方案、世界观呈现方式说明 |

### D3 — 角色体系设计文档

| 维度 | 内容 |
|------|------|
| 目标 | 定义角色的分类、数量、能力范围和成长机制 |
| 输入 | D5 的阵营划分结论、D1 的单局流程结论 |
| 输出 | 角色分类表、角色能力描述模板、角色数量与人数映射表 |

### D4 — 道具与卡牌体系文档

| 维度 | 内容 |
|------|------|
| 目标 | 定义卡牌的分类、数量、效果模板和使用规则 |
| 输入 | D1 的单局流程、D3 的角色体系、D5 的胜利条件 |
| 输出 | 卡牌分类表、卡牌效果模板、单局卡牌数量建议、卡牌数据结构建议 |

### D5 — 阵营与胜利条件文档

| 维度 | 内容 |
|------|------|
| 目标 | 定义阵营划分方式、各阵营的胜利条件、胜利判定机制 |
| 输入 | D1 的单局流程、D2 的世界观设定 |
| 输出 | 阵营划分方案表、胜利条件清单、胜利判定逻辑描述 |

### D6 — 文档结构总表

| 维度 | 内容 |
|------|------|
| 目标 | 汇总所有文档的索引、版本状态和依赖关系 |
| 输入 | D1-D5、D7-D9 的产出结果 |
| 输出 | 文档目录表、文档状态看板、更新记录 |

### D7 — 流程图集合

| 维度 | 内容 |
|------|------|
| 目标 | 将 D1 的单局流程可视化为流程图 |
| 输入 | D1 的单局流程设计文档 |
| 输出 | 单局流程图（Mermaid 或图片格式）、状态转换图 |

### D8 — 架构图与关系图

| 维度 | 内容 |
|------|------|
| 目标 | 可视化系统架构、模块关系、数据结构关系 |
| 输入 | D1-D5 的结论、技术方向说明 |
| 输出 | 系统架构图、模块关系图、数据流图 |

### D9 — MVP 边界收敛文档

| 维度 | 内容 |
|------|------|
| 目标 | 从所有规划中收敛出 MVP 最小可行范围，明确"做"与"不做" |
| 输入 | D1-D5 的全部结论 |
| 输出 | MVP 功能清单、明确不做清单、MVP 验收标准 |

## 6. 制作顺序：哪些必须先做，哪些可以后做

### 第一优先级（必须最先完成）

1. **D2 — 剧情背景设定文档**（解决 Q8 原著边界问题）
2. **D1 — 单局流程设计文档**（解决 Q1 核心循环问题）
3. **D5 — 阵营与胜利条件文档**（解决 Q3/Q4 阵营与胜利问题）

> 理由：这三份文档分别解决版权边界、核心玩法、胜利目标三大基础问题，后续所有设计都依赖它们。

### 第二优先级（依赖第一优先级产出）

4. **D3 — 角色体系设计文档**（依赖 D5 的阵营划分）
5. **D4 — 道具与卡牌体系文档**（依赖 D1、D3、D5）

### 第三优先级（文档工程化）

6. **D6 — 文档结构总表**（汇总前 5 份文档）
7. **D7 — 流程图集合**（可视化 D1）
8. **D8 — 架构图与关系图**（可视化全局）

### 第四优先级（收敛与收口）

9. **D9 — MVP 边界收敛文档**（基于全部文档收敛 MVP 范围）
10. **D10 — 单文档成稿模板**（标准化文档格式，可与其他文档并行准备）

### 可并行的部分

- D1、D2、D5 可在确定依赖前提后**并行开展**（分别交给不同 AI）
- D6、D7、D8 可在 D1-D5 完成后**并行产出**

## 7. 阶段 0 的验收标准

阶段 0 完成，当且仅当以下所有条件满足：

| 编号 | 验收项 | 判定标准 |
|------|-------|---------|
| V1 | D1-D5 全部产出 | 每份文档有明确的结论，不含"待定"项 |
| V2 | 原著引用边界已明确 | 有可用的元素清单、禁用清单和原创替换方案 |
| V3 | 单局核心循环已定义 | 能完整描述一局游戏从开始到结束的每个阶段 |
| V4 | 胜利条件已定义 | 每个阵营的胜利条件可被明确判定 |
| V5 | 卡牌与角色体系已定义 | 有分类表、数量建议和数据结构建议 |
| V6 | MVP 范围已收敛 | 有明确的"做"与"不做"清单 |
| V7 | 文档结构已建立 | 有 D6 文档结构总表，所有文档可索引 |
| V8 | 无版权风险 | 所有素材使用方式不依赖未授权的原著内容 |
| V9 | 技术架构已明确 | 有系统架构图和数据流图（D8） |
| V10 | 可进入阶段 1 | 阶段 1（MVP 可玩原型）的需求已足够清晰，可以开始编写 PRD |
