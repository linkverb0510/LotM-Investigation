- 新增房间页一屏布局所需的网格结构样式：

  - 新状态模型引入了更多资源和风险信息，因此需要更强的视觉层级去区分公共信息、个人资源和危险提示。

### `src/components/lobby-client.tsx`

- 修改原因：

  - 原逻辑足够简单，因此这轮只升级展示层，不增加理解负担。
  - 测试反馈表明“加入房间后没有进入感”，因此需要在成功入房后立即把用户带到房间页。

### `src/lib/server/socket-events.ts`

- `game:play` 事件补传 `targetPlayerId`。
- `game:state` 私有快照补传 `selfPlayerId`。
- `room:create` / `room:join` 后新增 `room:entered` 私有事件。
- 新增 `game:choose` 事件，把剧情抉择结果提交给服务端。
- 修改原因：
  - 某些卡牌需要目标，前端必须把目标参数带给服务端。
  - 前端不能靠玩家列表顺序猜测“哪个是我”，必须有显式身份标记，才能正确做灵性校验和目标过滤。
  - 仅靠公共 `room:updated` 很难让单个客户端明确知道“我已经成功进入房间”，因此补一个私有入房事件更稳定。
  - 引擎已经具备 `pendingChoice` 能力，如果分发层不把提交入口接出来，完整一局会卡在剧情抉择。

### `src/lib/server/room-store.ts`

- 在私有快照里补充 `readyPlayers`、`roleFaction`、`pendingChoice`、`hasPendingChoice`。
- 新增 `applyStoryChoice`。
- 修改原因：
  - `BriefingScreen` 需要知道目前有多少人已经准备。
  - 当前玩家需要知道自己的真实阵营类型，但前端展示时会把污染阵营模糊化，避免穿帮。
  - 抉择内容是私有叙事信息，不应该对所有客户端公开，所以这里只给目标玩家完整内容，其他玩家只知道“有抉择正在发生”。

### `src/lib/game/engine.ts`

- 新增 `finalizeRoundAfterResolution`，把“结算暂停后的收尾流程”抽成单独函数。
- `submitStoryChoice` 在清空 `pendingChoice` 后，不再重跑整轮结算，而是从暂停点继续推进。
- 修改原因：
  - 这是本轮唯一主动触碰核心引擎的地方，而且属于“阻断完整流程的致命问题修复”。
  - 如果抉择结束后重新执行整轮结算，卡牌效果会被重复应用，自动化测试和真实试玩都会得到错误结果。
  - 把“暂停点后的收尾逻辑”抽出来，是更专业的状态机做法：避免复制逻辑，也避免重复结算。

### `scripts/auto-test-game.ts`

## 关键实现说明

### 为什么这轮最终还是修改了 `src/lib/game/engine.ts`

原本这轮的边界确实是“先改前端和分发层”。  
但在补自动化测试脚本后，我确认 `pendingChoice` 会让回合停在一个“已完成大部分结算，但还没做收尾”的暂停点。

如果玩家完成抉择后直接重新跑整轮结算，就会重复应用卡牌效果。  
这已经不是“体验不佳”，而是“状态机错误”，会直接污染测试结果和真实对局结果。

所以这次修改 `engine.ts` 的原则是：
- 不改规则平衡
- 不改卡牌效果定义
- 只修复剧情抉择后的流程续跑

这属于专业工程里常见的“最小必要修复”。

### 为什么方案 A 要把手牌固定到底部

一个很实用的类比是桌游桌面：
- 公共信息通常放在桌面中央
- 个人手牌一定靠近自己

数字卡牌也遵循这个心理模型。  
把手牌放到底部，有两个直接收益：

- 玩家更容易形成操作习惯
- 中央区域就能留给“当前阶段最重要的事”

这就是方案 A 的核心价值：它不是单纯换布局，而是重新定义信息的归属关系。

### 为什么前端也要做灵性不足判断

服务端仍然是最终裁决者，这点没有改变。  
但从交互角度看，如果玩家点一张明显打不起的牌却没有即时反馈，体验会很差。  
因此这里在前端先做一次资源校验，目的是“更快反馈”，不是“取代服务端校验”。

### 为什么要引入目标选择弹窗

因为需要目标的卡牌如果仍然采用“一键出牌”，玩家就无法明确指定作用对象。  
这轮先用最直接的弹窗做目标选择，有两个好处：

- 结构直观，适合学习。
- 后续后端如果把目标规则做复杂，前端可以在现有流程上继续扩展，而不是推翻重做。

### 为什么 `briefing` 阶段必须彻底隐藏操作区

因为 P0 的作用是“叙事建立 + 身份揭示 + 全员准备”，而不是开始正式博弈。  
如果在这个阶段继续显示手牌和投票区，玩家会自然认为现在就能行动，结果一点击就报错，体验会很割裂。

所以这轮直接把 `briefing` 做成一个独立的全屏准备界面，让阶段边界在视觉上也成立。

### 为什么聊天要改成默认收起的抽屉

聊天当然重要，但在这个项目里，它不是主战斗控件。  
如果让聊天长期悬浮覆盖底部区域，用户会在最需要看手牌和阶段操作的时候被遮挡。

所以这轮把聊天降级为可展开抽屉，原因不是“弱化社交”，而是“先保护主界面的操作完整性”。

### 为什么自动化测试脚本默认选剧情抉择的第一项

这里不是在追求“最聪明的 AI 决策”，而是在追求“稳定回归”。  
对于自动化测试来说，优先级是：

1. 流程要能稳定跑完
2. 日志和阶段不能卡死
3. 抉择提交链路必须被覆盖

所以先用固定策略，是合理的 MVP 测试设计。后续如果你想做更高级的 bot，我们再升级。

## 已知限制

- 当前公开状态里没有其他玩家的真实 `role.title`，所以除了当前玩家外，其他玩家头衔只能保持未公开状态。这是后端公开数据边界导致的，不应由前端伪造。
- 自动化测试脚本虽然已经能跑通完整流程，但它还是保守 bot，不代表真实玩家行为的覆盖已经足够全面。
- 当前引擎仍然会出现“某玩家在某阶段没有可支付手牌”的情况；这不会阻断流程，但说明后续可能需要补“跳过行动”或“默认待机”机制，让日志更干净。
- 现有 `tests/engine.test.ts` 只覆盖了基础状态流，没有覆盖剧情抉择、Socket 事件和 UI 结构。
- `next build` 通过，但本机环境里仍有 `@next/swc-win32-x64-msvc` 的告警；目前不影响构建结果。
