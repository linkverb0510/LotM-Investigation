# 开发报告：引擎逻辑补全与 Dev Mode (Hermes Part)

> **日期**: 2026-05-14  
> **任务**: 封印物被动机制、Bot 托管逻辑、开发者控制台。

---

## 1. 需求与目标

*   **目标**: 完善游戏引擎，使其支持更复杂的被动规则（封印物副作用），并提供开发测试工具。
*   **受众**: 软件工程大二学生（代码需易读，逻辑需清晰）。
*   **核心指标**: 
    1.  封印物持有者每回合自动结算副作用（如污染度增加）。
    2.  房间内可开启“Bot 托管”，自动执行出牌和投票，方便单人测试。
    3.  提供“开发者控制台”，允许通过 Socket 发送指令强制修改游戏状态。

---

## 2. 实施细节

### 2.1 封印物被动结算 (`engine.ts`)

**逻辑设计**：
在每一轮结束时（`resolveRound`），遍历所有玩家的手牌和已打出的牌。
如果发现有 `type: 'artifact'` 且定义了 `cost.corruption_delta` 的卡牌，则立即增加玩家的污染度。

**代码位置**：
在 `applyCardEffect` 之后调用一个新的检查函数 `applyArtifactSideEffects`。

### 2.2 Bot 托管逻辑 (`engine.ts`)

**逻辑设计**：
新增 `getBotAction` 和 `getBotVote` 函数。
*   **出牌**：遍历手牌，筛选出灵性够用的牌，随机打出一张（50% 概率暗置）。
*   **投票**：随机投给除了自己以外的任何一名玩家。

**使用方式**：
在 `room-store.ts` 的 `applyTurnAction` 之后，检查是否有玩家是 Bot，如果是，则自动调用这些函数提交行动。

### 2.3 开发者控制台 (`room-store.ts` & `socket-events.ts`)

**逻辑设计**：
在 `RoomStore` 类中新增 `handleDevCommand` 方法，支持解析字符串指令：
*   `set_corruption 50` -> 将当前玩家污染度设为 50。
*   `set_spirit 10` -> 将当前玩家灵性设为 10。
*   `set_phase showdown` -> 强制将阶段切换为“最终对决”。
*   `next_round` -> 直接进入下一轮。

**Socket 接入**：
在 `socket-events.ts` 中注册 `game:dev_cmd` 事件，前端只需发送 `{ roomCode, command }` 即可触发。

## 3. 验证与兼容性

*   **安全性**：所有 Dev 指令仅在本地测试环境使用，正式部署时可关闭。
*   **状态一致性**：Bot 的逻辑完全基于当前 `GameState` 的公开信息（除了它自己的手牌），不会破坏状态机流转。

## 4. 学生笔记：如何理解这些代码？

### 4.1 为什么用 `Math.random()`？
在原型开发阶段，使用随机数是快速验证逻辑最简单的方法。后期可以替换为基于权重的算法（比如 Bot 优先攻击低灵性玩家），但在 MVP 阶段，随机性已经足够测试“多人同时行动”的同步逻辑。

### 4.2 `switch (cmd)` 的作用
这是实现**控制台指令**的标准写法。它接收一个字符串（如 "set_corruption"），通过 `switch` 匹配对应的逻辑分支，并解析参数（如 "50"）。这让开发者可以不修改代码就能改变游戏状态。

### 4.3 封印物的副作用机制
这是一种**被动触发 (Passive Trigger)** 的设计模式。与主动出牌不同，它不需要玩家操作，而是由系统在特定时间点（回合结算时）自动检查并执行。这种模式在卡牌游戏（如《炉石传说》的“奥秘”或《杀戮尖塔》的“遗物”）中非常常见。
