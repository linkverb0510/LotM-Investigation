## 1. 审查目标

本轮审查的目标不是“删文件”，而是把 `docs/` 从“开发过程中自然堆积的资料夹”整理成“可长期维护的项目文档系统”。

核心判断标准有 4 个：

1. 这份文档是否仍然代表**当前项目的真实状态**。
2. 这份文档是否与别的文档存在**重复、冲突或上下位关系不清**的问题。
3. 这份文档是否属于**活文档**，还是仅属于**历史过程记录**。
4. 这份文档是否应该继续放在当前目录，还是应转入统一的 `docs/archived/`。

## 2. 当前文档盘点

当前 `docs/` 共包含：

- `60` 个 Markdown 文档
- `6` 个 PNG 文件
- `1` 个 PDF 文件
- `1` 个调试日志文件
- 合计 `68` 个文件

## 3. 主要结构问题

### 3.1 活文档与历史文档混放

现在的 `docs/` 同时混有：

- 当前仍需持续维护的活文档
- 某一轮开发结束后留下的过程报告
- 早期阶段 0 草案
- 测试临时记录
- 调试产物

这样会带来一个直接问题：**后来者很难判断“该看哪份才算当前版本”。**

### 3.2 同主题多版本并存

目前最明显的重复有：

- `docs/本轮开发计划.md` 与 `docs/开发相关文档/本轮开发计划.md`
- `docs/设定相关文档/剧情背景设定文档.md` 与 `docs/设定相关文档/剧情背景设计文档.md`
- `docs/characters/02-tarot-messenger.md` 与 `docs/characters/02-magician.md`、`docs/characters/02-灰雾魔术师.pdf`

这类重复不是“备份”，而是会造成认知冲突。工程上应尽量只保留一个明确的主版本，其余进入归档。

### 3.3 阶段 0 设定稿与当前实现状态未完全对齐

部分阶段 0 文档仍然有设计价值，但它们的内容已经和当前角色卡、前端状态字段、引擎阶段模型不完全一致。  
这类文档不应继续被误认为“当前有效规范”，但也不应粗暴删除。

最典型的是：

- `docs/设定相关文档/角色体系设计文档.md`
- `docs/设定相关文档/道具与卡牌体系文档.md`
- `docs/设定相关文档/阵营与胜利条件文档.md`

因此我把它们列入“待你拍板”的边界区，而不是直接判死刑。

### 3.4 目录命名与职责还不够稳定

目前同时存在：

- 中文功能目录：`开发相关文档`、`设定相关文档`、`测试问题`
- 英文功能目录：`plans`、`reviews`、`study-notes`、`dev-reports`
- 专题目录：`characters`、`cards`、`Items`、`plot`

这不是错误，但说明目录的“层次规则”还没完全稳定。  
建议先确定“哪些目录代表当前主文档，哪些目录只承载过程资料”，再执行第二轮重排。

## 4. 建议的主文档分层

我建议将 `docs/` 的长期主结构稳定为下面这套：

```text
docs/
  开发相关文档/               # 长期规划、架构、流程、开发日志
  设定相关文档/               # 世界观、剧情、角色体系、阵营规则等高层设定
  characters/                 # 面向实现与展示的角色卡、角色图
  plans/                      # 当前仍有参考价值的专题计划
  reviews/                    # 正式审查报告、阶段审查、文档审查
  test-reports/               # 自动化测试与验收报告
  troubleshooting/            # 故障排查手册
  ui-references/              # UI 参考与分析模板
  game-design-references/     # 玩法参考与模板
  codex-prompts/              # 面向 Codex/Hermes 的任务提示词
  archived/                   # 统一归档目录
```

### 为什么这样分

一个简单类比：  
主书架上应该摆“还在看的书”，储物箱里放“已经读过但以后可能会翻”的资料。

专业上，这对应的是：

- **Active Docs**：当前规范、当前计划、当前参考
- **Historical Docs**：历史方案、执行记录、旧草稿、调试副产物

把两者分开后，项目文档就会更像一个工程体系，而不是聊天记录的沉淀物。

### 5.2 建议保留，但必须更新

这类文档的“存在位置”是对的，但内容已经明显滞后：

- `docs/本轮开发计划.md`
  - 应继续作为“每轮开发前的唯一计划入口”，但下次进入实现前必须覆盖为新一轮计划。
- `docs/开发相关文档/文档结构总表.md`
  - 仍然有索引职责，但内容停留在较早的 D0-D9 结构，未反映现在的文档实际布局。
- `docs/dev-reports/progress-tracker.md`
  - 它是最像“项目总进度看板”的文件，但内容已经落后于当前 UI 与测试进展。

### 5.3 建议归档

这类文档的主要问题不是“质量差”，而是**已经完成其历史使命**，再继续留在活目录里会制造混乱：

- 旧版角色草稿与重复文件
- 已执行完成的阶段计划
- 早期卡池速记稿
- 测试问题临时清单
- 开发当天的过程报告
- 调试日志

这些文档都建议转入 `docs/archived/` 下的分类目录。

### 5.4 待你确认的边界文档

有 4 份文档我不建议直接替你拍板，因为它们属于“有价值，但已不完全同步当前状态”的中间地带：

1. `docs/testing-guide.md`
   - 若你需要一份“当前可执行的测试手册”，应重写后保留。
   - 若短期不维护人工测试流程，则应先归档。

2. `docs/设定相关文档/角色体系设计文档.md`
   - 它有很强的阶段 0 策划价值。
   - 但当前已经被 `docs/characters/` 的角色卡体系部分取代。

3. `docs/设定相关文档/道具与卡牌体系文档.md`
   - 它仍是系统层卡牌设计稿。
   - 但与当前实现、当前卡池粒度并非完全一致。

4. `docs/设定相关文档/阵营与胜利条件文档.md`
   - 仍然有设计方向价值。
   - 但若继续保留在活文档区，容易被误认成当前最终规则。

## 6. 我建议的执行顺序

如果你确认本次规范化方向，后续执行顺序建议如下：

1. 先建立统一的 `docs/archived/` 目录骨架。
2. 优先移动“重复文件”和“明显过时文件”。
3. 再移动“历史计划 / 过程日志 / 临时测试问题”。
4. 最后处理 4 份“待你确认”的边界文档。
5. 归档完成后，再统一更新：
   - `docs/开发相关文档/文档结构总表.md`
   - `docs/dev-reports/progress-tracker.md`
   - `docs/本轮开发计划.md`

## 7. 本次结论

### 结论一句话版

当前 `docs/` 的问题，不是文档不够多，而是**活文档、历史文档、草稿和调试产物混在了一起**。  
正确的整理方式不是重写一切，而是先把“谁是当前主版本”明确出来，再把旧资料有组织地归档。
