# 房间页一屏布局草案

## 文档目的
这份文档用于把研究结论转成可以落地讨论的布局方案。  
这里先不进入编码，而是先把 3 套结构方案摆清楚，让你可以判断哪一种最符合你想要的游戏气质和后续实现节奏。

## 先说结论
如果目标是：
- 一屏可见
- 桌面端优先
- 兼顾卡牌操作和社交推理
- 尽量不把前端结构做得过于复杂

那么优先级建议是：
1. 方案 A：底部手牌 + 中央视角主舞台
2. 方案 B：讨论强化型指挥台
3. 方案 C：双态切换式布局

---

## 方案 A：底部手牌 + 中央视角主舞台

### 适合场景
这是最稳妥、最接近主流数字卡牌的布局。  
如果你希望玩家一进入界面就知道“我在玩一款卡牌游戏”，它最合适。

### 页面分区

#### 顶部 HUD
- 房间号
- 当前阶段
- 当前回合
- 当前行动者
- 仪式进度条
- 倒计时

#### 左侧窄栏
- 玩家头像/名字
- 灵性条
- 污染值
- 线索数
- 当前回合高亮

说明：
左栏只保留“扫一眼就懂”的数据，不展示过长文本。

#### 中央主舞台
- 阶段说明
- 中央日志
- 当前阶段操作引导
- 调查阶段的事件提示
- 讨论阶段的投票面板

说明：
中央区域始终承担“当前最重要的内容”，它不是死板的日志墙，而是可根据阶段切换重心。

#### 底部手牌托盘
- 横向卡牌列
- 选中卡牌后上浮显示详情
- 需要目标时触发中央目标选择态

#### 右侧折叠区
- 聊天
- 扩展日志
- 系统提示

### 关键交互

#### 出牌
1. 在底部点击卡牌
2. 若资源不足，直接在卡牌附近给出错误提示
3. 若需要目标，中央舞台切换为“选择目标”
4. 确认后恢复中央舞台

#### 投票
1. 进入讨论阶段后，中央主舞台切换为投票视图
2. 左侧玩家列仍保留，供观察所有人状态
3. 玩家点击投票对象后，在中央确认

### 优势
- 最符合卡牌用户习惯
- 手牌终于回到底部，操作路径更自然
- 页面结构稳定，后续迭代成本低
- 适合保留现有日志、投票、目标选择逻辑

### 代价
- 左侧玩家列表会更紧凑，单个玩家卡的信息量必须压缩
- 中央区域的“日志”和“投票”需要做阶段切换，不能同时都展开

### 粗略草图

```text
┌────────────────────────────────────────────────────────────┐
│ 顶部 HUD: 房间 | 阶段 | 回合 | 当前行动者 | 仪式进度 | 倒计时 │
├───────────────┬───────────────────────────────┬───────────┤
│ 左侧玩家状态栏 │ 中央主舞台（日志 / 引导 / 投票 / 抉择） │ 右侧抽屉区 │
│ 玩家1          │                               │ 聊天/扩展  │
│ 玩家2          │                               │            │
│ 玩家3          │                               │            │
├───────────────┴───────────────────────────────┴───────────┤
│ 底部手牌托盘：卡牌1 | 卡牌2 | 卡牌3 | 卡牌4 | 卡牌5         │
└────────────────────────────────────────────────────────────┘
```

## 方案 B：讨论强化型指挥台

### 适合场景
如果你认为这个项目的核心不是“卡牌”，而是“带卡牌资源管理的社交推理”，那么这套会更贴题。

### 页面分区

#### 顶部 HUD
与方案 A 相同，但可以更紧凑。

#### 左中大区
- 玩家关系面板
- 当前发言对象
- 投票状态
- 可疑度观察区域

说明：
这部分视觉权重最大，更像“会议桌”。

#### 右中区
- 中央日志
- 当前阶段说明
- 系统事件

#### 底部双层操作区
- 第一层：快捷操作按钮
- 第二层：手牌托盘

### 关键交互

#### 调查阶段
- 底部手牌仍能操作
- 中央右区提供日志与结果反馈
- 左中区主要显示玩家状态

#### 讨论阶段
- 左中区升级为主舞台
- 投票和发言判断成为主视角
- 手牌弱化但仍保留

### 优势
- 更突出“社交推理”
- 讨论阶段体验会比方案 A 更强
- 玩家更容易把注意力放在“人”而不是“卡”

### 代价
- 调查阶段会显得没那么像传统卡牌界面
- 需要更细致地处理“讨论阶段”和“调查阶段”的视觉切换
- 对前端布局状态管理要求更高

### 粗略草图

```text
┌────────────────────────────────────────────────────────────┐
│ 顶部 HUD: 房间 | 阶段 | 回合 | 当前行动者 | 仪式进度 | 倒计时 │
├───────────────────────────────┬────────────────────────────┤
│ 左中主舞台：玩家关系 / 投票 / 怀疑 │ 右中区：日志 / 系统事件 / 引导   │
│ 玩家卡更大、更显眼                │                            │
│ 讨论阶段这里成为核心              │                            │
├────────────────────────────────────────────────────────────┤
│ 底部快捷操作：投票 / 结束行动 / 打开聊天 / 展开目标选择      │
├────────────────────────────────────────────────────────────┤
│ 底部手牌托盘：卡牌1 | 卡牌2 | 卡牌3 | 卡牌4 | 卡牌5         │
└────────────────────────────────────────────────────────────┘
```

## 方案 C：双态切换式布局

### 适合场景
如果你希望“调查阶段”和“讨论阶段”在视觉上明显不同，这套最有戏剧感。

### 页面分区思路
它不是一套固定布局，而是两套近亲布局：

#### 调查态
- 顶部 HUD
- 中央日志/事件舞台
- 左侧玩家状态
- 底部手牌

#### 讨论态
- 顶部 HUD
- 中央投票/发言舞台
- 左右两侧是玩家与票型
- 手牌缩成窄条或次级面板

### 关键交互

#### 调查阶段
用户体验接近方案 A。

#### 讨论阶段
页面像进入“会议模式”，投票区与玩家信息全面上浮。

### 优势
- 最符合阶段式游戏节奏
- 玩家会明显感觉“游戏进入了新阶段”
- 讨论体验和调查体验都能分别优化

### 代价
- 实现复杂度最高
- 前端组件拆分和状态同步要做得更严谨
- 初学者后续维护成本更高

### 粗略草图

```text
调查态
┌────────────────────────────────────────────────────────────┐
│ 顶部 HUD                                                   │
├───────────────┬────────────────────────────────────────────┤
│ 玩家状态       │ 中央日志 / 当前事件 / 目标选择               │
├───────────────┴────────────────────────────────────────────┤
│ 底部手牌托盘                                               │
└────────────────────────────────────────────────────────────┘

讨论态
┌────────────────────────────────────────────────────────────┐
│ 顶部 HUD                                                   │
├────────────────────────────────────────────────────────────┤
│ 中央会议舞台：发言 / 投票 / 指向关系 / 当前焦点人物          │
├───────────────┬───────────────────────────────┬───────────┤
│ 玩家列表       │ 票型或讨论日志                  │ 聊天/记录   │
├────────────────────────────────────────────────────────────┤
│ 底部窄条：手牌摘要 / 快捷操作                                │
└────────────────────────────────────────────────────────────┘
```

## 三套方案的横向比较

| 维度 | 方案 A | 方案 B | 方案 C |
| --- | --- | --- | --- |
| 一屏可见能力 | 高 | 高 | 高 |
| 卡牌操作直觉 | 高 | 中 | 高 |
| 社交推理氛围 | 中 | 高 | 高 |
| 实现复杂度 | 低 | 中 | 高 |
| 后续维护成本 | 低 | 中 | 高 |
| 适合当前项目阶段 | 很适合 | 适合 | 暂时偏重 |

## 推荐方案

### 推荐：方案 A
理由：
- 它最容易把“显示不全”的问题一次性解决。
- 它对现有代码结构最友好，重构风险最低。
- 它最适合作为第一轮可落地的桌面版一屏布局。
- 后续如果你想继续强化讨论体验，还可以在方案 A 的基础上局部吸收方案 B 的想法。

### 次推荐：方案 B
如果你已经明确把“社交推理感”放在“卡牌操作直觉”之前，可以选它。  
但从当前项目阶段看，它更像第二轮 UI 深化，而不是第一轮止血重构。

### 暂不推荐直接上：方案 C
它最有表现力，但也最重。  
对于当前项目来说，它容易把“先把界面整理清楚”升级成“做两套完整 UI 系统”，性价比不够高。

## 给你的选择建议
如果你想尽快推进下一步实现，可以直接在下面三种意图中选一个：

1. 选方案 A，优先做稳定的一屏卡牌布局。
2. 选方案 B，优先做更强的社交推理舞台感。
3. 以方案 A 为底，再混入方案 B 的讨论强化设计。

## 当前阶段结论
到这里应该停下来，等待你确认方案。  
在你选定方案之前，不应直接开始改 `room-client.tsx`。
