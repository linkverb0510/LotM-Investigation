# MVP 边界收敛文档 — 调查模式

> 本文档定义当前 MVP 的明确边界。  
> 当前 MVP 只服务 `调查模式`，目标是验证“叙事驱动的超凡案件推理局”是否成立。

---

## 1. MVP 核心目标

做出一个能完整打一局的贝克兰德案件原型，让玩家在 3-6 人房间中体验：

- 固定角色 + 可变隐情
- 行动卡驱动的调查与非凡介入
- 有明确输入和后果的案件讨论
- 带《诡秘之主》气质的案件收束与余波结局

---

## 2. MVP 范围定义

### 2.1 必须做

| 模块 | 详细需求 |
|---|---|
| 核心流程 | P0(案情简报) → P1(第一轮行动) → P2(第一轮讨论) → P3(第二轮行动) → P4(第二轮讨论) → P5(收束阶段) → P6(余波结局) |
| 角色与隐情 | 固定角色、可变隐情、隐藏立场或隐藏压力源 |
| 行动卡体系 | 至少覆盖搜证、接触、压制、掩饰、净化、调度、封印物 |
| 资源系统 | 灵性消耗、污染累积、状态标签与少量关键物件控制 |
| 讨论机制 | 无淘汰制，讨论后产出案件决策与集体措施 |
| 叙事事件 | 公共案件事件 + 私密角色事件 + 至少 1 类行为反应事件 |
| 网络联机 | 房间制实时同步，支持准备、断线重连、对局推进 |
| 结局复盘 | 输出案件真相、角色后果、组织余波 |

### 2.2 暂不做 / 延后

| 模块 | 原因 / 替代方案 |
|---|---|
| 对决模式 | 预留为未来路线，不进入当前 MVP |
| 多案件池 | 当前先做单核心案件 + 高变体 |
| 22 条途径 | MVP 只覆盖当前角色与少量共享语法需要 |
| 复杂成长体系 | 不做跨局养成、晋升树、收藏系统 |
| 语音聊天集成 | 玩家使用外部语音工具，游戏内保留文字或最小沟通入口 |
| 复杂观战系统 | 先把实际玩家对局做通，再考虑扩展 |

## 3. 当前 MVP 的产品判断标准

### 玩家层

- 玩家能说清自己为什么要调查、为什么要讨论、为什么要在最后做收束选择
- 玩家能感受到《诡秘之主》的组织、序列、污染与封印物气质
- 玩家不会把这局描述成“贴皮狼人杀”或“没打起来的卡牌游戏”

### 设计层

- 单局每个阶段都有清晰输入、输出与状态变化
- 讨论后果能真实改变下一阶段行为权限或目标优先级
- 战斗型序列在调查模式中也有明确职责，如压制、封锁、护送、强制介入

### 工程层

- 服务端可推进完整一局
- 前端能明确区分玩家可见层与设计/调试层
- 关键结算和阶段切换可被日志或复盘说明

---

## 4. 技术与实现边界

当前文档只定义产品边界，不要求立刻扩展技术栈。

当前原型应继续遵守：

- 服务端权威状态机
- 房间制实时同步
- 玩家视角与系统视角分层
- 规则、角色、卡牌尽量数据化

不因为这轮调查模式收束而主动引入新的库或新的长期依赖。

---

## 5. 开发模式（Dev Mode）要求

即使当前只做调查模式，仍建议保留以下开发友好能力：

| 特性 | 说明 |
|---|---|
| 多窗口调试 | 支持在本地同时模拟多个玩家视角 |
| 控制台指令 | 用于快速跳转阶段、注入测试状态、验证讨论后果 |
| Replay / Log | 能回看阶段推进、关键决策和事件触发 |
| 最小 Bot 托管 | 仅用于补满房间和跑基础流程，不追求高智商表现 |

## 6. 当前建议里程碑

| 阶段 | 目标 | 交付物 |
|---|---|---|
| M0 | 文档定稿 | 调查模式主文档体系 |
| M1 | 流程跑通 | 能完整走完 P0-P6 的网页原型 |
| M2 | 叙事落地 | 核心案件、私密事件、结局余波能够被实际触发 |
| M3 | 体验打磨 | 界面信息层级、讨论引导、结局复盘更自然 |
